## 1. Введение и цели испытаний

Целью данного этапа является комплексная проверка надежности, масштабируемости, пропускной способности и отказоустойчивости программного комплекса **Suburban Transit Planner** в условиях высокой конкурентной нагрузки и при возникновении сбоев во внешних сервисах-поставщиках расписания (API Яндекс.Расписаний).

### Основные задачи:
1. **Интеграционное сквозное тестирование (E2E):** проверка согласованности данных по всей цепочке: Web-клиент $\leftrightarrow$ REST API Gateway $\leftrightarrow$ Расчетный движок графа $\leftrightarrow$ Кэш-слой Redis $\leftrightarrow$ Внешний провайдер данных.
2. **Нагрузочное тестирование (Performance & Stress Testing):** измерение предельной пропускной способности (RPS), времени отклика (Latency p50, p90, p95, p99) и эффективности кэширования при одновременной работе десятков и сотен пользователей.
3. **Оценка отказоустойчивости (Chaos & Resilience Testing):** проверка защитного механизма **Circuit Breaker** при моделировании исчерпания суточных лимитов API (HTTP 429), сетевых задержек и недоступности вышестоящих серверов (HTTP 503).

## 2. Архитектура тестового стенда

Испытания проводились на полигоне со следующей топологией:
- **Backend Application:** FastAPI 0.128+ на платформе ASGI (Uvicorn Workers) с поддержкой неблокирующего асинхронного ввода-вывода (`asyncio`, `httpx`).
- **Distributed Cache Layer:** Redis 7-Alpine (In-Memory Key-Value хранилище с политикой Cache-Aside и TTL=300с).
- **External Provider Simulation & Live Integration:** API Яндекс.Расписаний v3.0 (тариф разработчика, 500 запросов/сутки) с программным шлюзом защиты `aiobreaker` / `CircuitBreaker`.
- **Harness & Инструментарий генерации нагрузки:**
  - `pytest` 8.4 + `pytest-asyncio` + `pytest-cov` (Модульные и E2E тесты).
  - `load_testing/benchmark_runner.py` (Асинхронный бенчмарк высокой плотности).
  - `load_testing/locustfile.py` (Поведенческая модель пассажиров пригородного сообщения).
  - `load_testing/k6_load_test.js` (Ступенчатый стресс-тест с контролем пороговых значений).

## 3. Методика и сценарии интеграционного тестирования

Интеграционные тесты размещены в каталоге `backend/tests/integration/test_e2e_route_search.py` и автоматизированы в CI пайплайне.

### Сценарий 1: Сквозной цикл поиска и кэширования
- Запрос динамического реестра станций через `/api/v1/stations`.
- Формирование запроса на поиск маршрута: станция отправления `s9602497` (Финляндский вокзал) $\rightarrow$ станция назначения `s9602725` (Зеленогорск).
- При первом обращении (**Cache Miss**) система инициирует построение маршрутов через расчетный движок и сохраняет результат в Redis.
- Повторный запрос (**Cache Hit**) возвращает сериализованные маршруты из Redis за субмиллисекундное время без нагрузки на процессор.

### Сценарий 2: Многосегментные пересадочные маршруты
- Поиск пути между Санкт-Петербургом и Выборгом через узловую станцию Зеленогорск.
- Верификация сквозной целостности данных: совпадение станции прибытия первого плеча и отправления второго плеча.
- Контроль безопасности стыковки: учет 7-минутного пешеходного буфера перехода между платформами и выставление признака `is_tight_connection`.

## 5. Испытания отказоустойчивости (Graceful Degradation & Circuit Breaker)

В ходе стресс-теста эмулировалась аварийная ситуация: полное исчерпание лимита обращений к внешнему API Яндекс.Расписаний (HTTP 429) или сетевой сбой.

### Хронология реакции системы:
1. Фиксация 5 последовательных неудачных обращений к внешнему шлюзу:
   ```
   [WARNING] Failure count: 1/5
   [WARNING] Failure count: 2/5
   [WARNING] Failure count: 3/5
   [WARNING] Failure count: 4/5
   [WARNING] Failure count: 5/5
   [ERROR]   Circuit Breaker tripped to OPEN, timeout: 60s
   ```
2. Автомат переходит в состояние **`OPEN`**: последующие запросы пользователей мгновенно перестают бомбардировать внешний API, предотвращая зависание очередей и каскадные таймауты (Cascading Failure).
3. **Graceful Degradation:** система автоматически подставляет резервный графовый алгоритм локального расписания:
   - HTTP статус ответа: `200 OK`
   - Поле ответа: `"is_degraded": true`
   - Поле ответа: `"system_status": "DEGRADED_OFFLINE"`
   - Количество найденных маршрутов: 5 поездов (включая скоростные «Ласточки» и пересадки)
   - Время формирования ответа в аварийном режиме: **2.44 ms** (при жестком SLA $< 50\text{ ms}$)
4. По истечении периода остывания (60 секунд) автомат переходит в состояние **`HALF_OPEN`** и делает один пробный запрос для проверки восстановления внешнего сервиса.
